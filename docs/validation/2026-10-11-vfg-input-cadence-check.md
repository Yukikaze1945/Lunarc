# VFG 输入与成品时序排查

## 范围

排查用户反馈的补帧成品更卡顿。素材为 `Bulgaria 4K HDR 60P _fantav.com.mkv`，
成品为同目录 `_dlss.mkv`，3840×2160，2× VFG。
未更改生产代码、用户导出文件或播放器设置。

## 输入契约

与 NVIDIA [VFG 文档](https://docs.nvidia.com/maxine/vfx/latest/Filters/VideoFrameGeneration.html)
逐项核对：前帧绑定 `SrcImage0`，后帧绑定 `SrcImage1`，2× 固定模式
设置 `FrameMultiplier=2`、`FrameIndex=1`。生成帧同步消费，再覆盖输出缓存。
HDR 边界三个图像均为 RGB10A2，主色保持 FP16。当前输入先保留，前帧另存，
未发现前后输入指针相互覆盖的代码路径。

## 实际接口测试

直接调用当前原生 VFG DLL，在 CUDA 上以 1280×720 纹理测试四对连续输入。
相邻原帧整体水平平移 8 像素。8-bit RGBA 与 RGB10A2 分别测量，
生成帧相对前帧的平移均约为 4 像素：

- RGBA8：3.933、3.961、3.977、3.998 像素。
- RGB10A2：3.894、3.935、3.960、3.993 像素。

测试显式关闭自动镜头切换检测，manual ShotChange=0，隔离输入方向与时间位置。
采用固定 low 模式；这是接口正确性测试，不是模型画质或性能 benchmark。
诊断过程使用 host upload/readback，不能计作生产零图像回读证据。

## 用户整段成品

读取整个视频的 packet PTS 集合，而非重新渲染：

| 项目 | 源视频 | 成品 |
| --- | --- | --- |
| 视频 packet 数量 | 20,338 | 40,676 |
| 唯一 PTS 数量 | 20,338 | 40,676 |
| 首 PTS | 0 | 0 |
| 尾 PTS | 339,289 | 339,298 |
| 相邻展示时间间隔 | 16 / 17 ms | 8 / 9 ms |
| 异常长 PTS 间隔 | 无 | 无 |

另外逐项比较，成品所有偶数位置的 PTS 与源 PTS 完全相同，
即原帧时间点完整保留，补帧插入在其间。

此检查按 PTS 排序；HEVC packet 在文件中的 decode order 与 display order 不同。
整段时间戳检查并不证明每幅画面的内容都有正确运动。

另取 0、10、30、60、120 秒附近的各 36 张源帧和 74 张输出帧，
软件解码到 512×288 灰度后按实际 PTS 对齐原帧与中间帧。
有运动的 121 对样本中，120 对的中间帧不像简单复制端点
（启发式：距最近端点的 MAE / 端点间 MAE < 0.12 判为类似端点）。
各区间该比率中位数约 0.515～0.536，未发现普遍重复帧。
唯一类似端点的样本不能据此判定 SDK 错误；微小运动、压缩、镜头变化都可能影响该指标。

不能直接把 seek 后的第偶数帧当原帧：例如 seek 到 10 秒后，
成品第一张为中间帧，源第一张则为原帧。不对齐实际 PTS 会制造错误的重复帧判断。

证据：`bench_out/vfg_cadence_20261011/` 中的
`timestamps.json`、`analysis.json`、`native_pair.json` 及复现脚本。

## 尚未确定

目前证据不支持“前后帧输入接反”“普遍复制端点”或“输出帧时间戳混乱”。
用户实际播放器、卡顿具体时间点、硬件解码状态、播放丢帧计数和显示刷新率尚待确认。
未把卡顿归因于播放器，也未宣称所有场景下 VFG 画质正确。
