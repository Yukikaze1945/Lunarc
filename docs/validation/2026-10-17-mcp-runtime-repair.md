# 旧独立运行环境的 MCP 启动修复

## 原因

源码启动器实际选用了 `build/standalone-runtime/python/python.exe`（CPython 3.10.18），该旧环境缺少新增加的 MCP/HTTPX。先前在其他 Python 环境的通过结果不能证明这个启动器可用。新增依赖又被列为整个工作台启动的必要条件，因而弹出启动失败。

## 修复

- 为实际使用的独立环境安装 MCP 2.0.0、HTTPX 0.28.1 及所需依赖。仅已有的 idna 从 3.11 更新为 3.20；原有 Torch、CUDA、FastAPI、OpenCV 等另外 33 个发行包版本均保持不变。
- 该环境关闭了 site 钩子，PyWin32 因而缺少路径。为 `_pth` 增加四个相对私有路径，保留隔离模式；同步修正运行时构建器。没有开启用户 site 或引入其他应用的包。
- 备份并更新运行时清单，仅重算新增/更改包及 `_pth` 的文件项，未重新读取或哈希整个 Torch 目录。
- MCP/HTTPX 检查改为集成能力检查；它们缺失时核心启动检查仍可通过。HTTP MCP 工厂提供明确的不可用响应，并通过设置面板显示原因，避免依赖缺失导致整个后端无法导入。

## 验证

- 26 项回归通过，包含缺失 SDK/HTTPX 时核心接口仍能启动、MCP 明确报错及权限检查。
- 完全复用 Electron 的解释器选择、`-I`、独立 PATH 与环境检查：`ready=true`，失败项为空。
- 同一解释器和隔离环境下实际导入软件后端与 HTTP MCP 成功。
- 重新打开源码运行版，实际后端健康检查为正常（Python 3.10.18）；活动任务为空，队列未运行。
- 对正在运行的真实 `/mcp` 进行客户端初始化、工具列举和只读状态调用：Lunarc、13 个工具、成功结果。

没有启动模型渲染或导出。版本快照、清单备份及实际启动证据位于本机 `runtime/validation/mcp-runtime-repair/`，没有发布安装包。
