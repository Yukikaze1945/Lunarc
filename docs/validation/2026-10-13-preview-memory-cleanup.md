# 预览异常与显存检查

## 原始日志能够说明什么

2026-10-13 12:40:37 的一次 `access violation reading 0x910` 后，出现六次 `host already active`。这与原生调用中断后未完整释放进程级 NGX 状态一致；`host already active: 0x00000000` 中的零是错误函数传入的详情，不是这次访问异常的地址。

原日志只记录异常文字，没有调用栈。不能据此证明首次异常一定发生在 `dlss_gpu_host_open`，也不能确定 `0x910` 是哪个对象的成员偏移；重建包含旧管线关闭和新管线打开，二者都需要检查。

## 74 GB 计数器的局限

同一旧进程的一次实际采样：

| 项目 | 字节或 MiB |
| --- | ---: |
| Windows GPU Process Memory DedicatedUsage | 76,822,061,056 字节，约 71.55 GiB |
| 同一计数器 TotalCommitted | 2,610,913,280 字节，约 2.43 GiB |
| SharedUsage | 373,567,488 字节 |
| NVIDIA 驱动报告的整张显卡占用 | 4,824 MiB |

这些值不是同一个测量口径，异常大的 DedicatedUsage 不能直接当作真实常驻显存，也不能作为“显存不足使指针失效”的因果证据。此前引用的 [GPU Process Memory 计数器虚增说明](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value)明确针对 Windows 10，不能据此判断 Windows 11 的原因。用户指出 DLAA 模型切换后，另做了本机 Windows 11 的逐次切换与 DXGI 采样，见 [DLAA 模型切换检查](2026-10-13-dlaa-model-memory.md)。

## 短重建检查

素材为 3840×2160、120 fps、AV1、BT.709 SDR 10-bit。使用用户的单层 NR → TrueHDR 设置，每次只处理一帧，工作缩放按 100% → 75% → 100% 触发三个真实会话重建。

| 原始实现，整卡占用 | MiB |
| --- | ---: |
| 测试前 | 4,828 |
| 第一次 100% | 8,639 |
| 75% | 7,913 |
| 再次 100% | 8,639 |
| 关闭处理管线后 | 4,900 |

没有观察到按重建次数累积的常驻显存增长，也没有复现原始访问异常。这是短检查，不能排除长时间、其他渲染链或瞬时峰值问题。

修改后的同路径检查中，两次 100% 占用均为 9,227 MiB，当轮基线为 5,633 MiB。相对当轮基线增加 3,594 MiB，原始实现增加 3,811 MiB。背景显卡负载发生变化，这个差值不是受控性能基准，不能宣称稳定节省 217 MiB。

原生 FP16 面板另做三个重建：在屏幕外的有效窗口实际执行 GPU 绘制与 Present，每轮计数为 2，显示图片回读为 0，未出现原始异常。隐藏父窗口的检查只覆盖资源上传及释放，不作为绘制证据。没有测屏幕刷新率或 4K 120 fps 推理性能。

## 本轮修正

- 预览显示或缓存关闭报错后，继续按依赖顺序清理模型、光流、解码器和加载器；保留首个错误和其他清理错误。
- SDR、HDR 及 SDR 多层基础链的释放不再因首个报错跳过其余资源，解码上下文仍最后释放。
- Python 在调用原生 host close 前清除其句柄，避免原生函数已经删除对象后，外层再次关闭同一个地址。
- 未完成的原生 host/layer 使用作用域所有权处理普通 C++ 异常；空的临时 NGX core 不再错误清除其他 host 的活动标记。这不代表可从任意 Windows 原生访问异常恢复。
- 预览记录完整 Python 调用栈和“关闭旧管线／打开新管线／处理帧”阶段。发生原生访问异常后拒绝继续复用该后端，避免反复调用可能损坏的 SDK 状态；需要重启恢复。
- CPU 颜色、CPU 光流和回读缓冲改为按接口需要分配。4K FP16 会话避免预分配 298,598,400 字节（约 284.77 MiB）逻辑缓冲；其中包括 CPU 上传与回读堆，不等于相同大小的物理显存节省，也不包含模型内部资源。

修改后的 GPU 链路由原生 `dlss_gpu_host_staging_bytes` 确认这些缓冲容量为零。RGBA8 和 RGBA16F 的 CPU 颜色、CPU 光流及运动回读短检查通过，按需分配后的输出有限、零运动保持零。

相关自动检查通过；一个原测试断言要求编码器关闭失败后停止后续释放，已改为检查所有剩余资源按顺序释放并保留原错误。证据在本机忽略目录 `build/preview-memory-20261013`。未运行全量测试或性能基准。原始 `0x910` 的具体原生故障位置仍未确定。

本轮源码和原生 DLL 已修改，GitHub 的 1.0.0 Beta 安装包尚未包含这些修正。
