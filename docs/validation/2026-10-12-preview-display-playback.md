# 预览映射与对比硬件解码

这是原生预览接入前的历史检查。当前工作台已使用 [原生 GPU 视频预览](../native-hdr-preview.md)，文件对比页仍沿用下文的 SDR 显示映射与硬件解码路径。

## 显示映射

当前工作台和视频对比仍通过 8-bit JPEG 显示。TrueHDR 输出会明确经过 HDR→SDR 映射，不声称原生 HDR 显示。

旧映射以 80-nit scRGB 单位直接压缩亮度，使升亮后的 TrueHDR 中高亮区域过于接近白色。现在使用固定 203-nit 显示参考；GPU 显示 shader 和 CPU 文件对比采用相同的亮度肩部压缩。映射不影响 NR、TrueHDR 或最终导出，不根据每帧峰值改变曝光。

320×192 的真实 GPU FP16 渐变检查确认 GPU／CPU 显示结果最大字节误差为 0，黑位与亮度顺序保持正确；测试渐变中点从旧映射的 237 降到 215，1000-nit 灰阶显示为 233，保留高亮显示余量。这不是显示器校准或主观画质验收。

## 视频对比

- 支持的 NVIDIA 解码输入明确使用 CUDA/NVDEC；通过 `scale_cuda` 在 GPU 缩到显示尺寸之后再回读，避免将完整 4K 帧传到 CPU 缩放。
- 两侧显示转换与 JPEG 编码并行执行，独立保持实际 PTS、两帧有界队列和最近帧选择。
- 不支持的编码/格式使用软件解码。GPU 启动失败只允许在尚未产生画面时回退一次，并在媒体信息中显示原因；不在播放中悄悄切换解码路径。
- 媒体信息显示实际解码器、GPU 缩放状态、显示尺寸及帧率。首次画面到达后再启动音轨；倍速播放的报文输出频率最高 60 Hz。
- 连续显示仍为最大 1280 宽、最高 60 fps。暂停和逐帧检查保留完整源尺寸和实际源帧；文件不改写。

## 本机短测

用户提供的《11.ハミングフレンド》原片为 AV1，导出文件为 HEVC；均为 3840×2160、120 fps、10-bit BT.709 SDR。

从媒体第 20 秒起，逐次请求 60 对画面，覆盖同一秒的素材时间。下表测量解码推进、显示转换、JPEG 编码及报文准备；不包含 WebSocket、浏览器绘制或显示器扫描。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 第一对画面准备 | 3396.1 ms | 897.9 ms |
| 每对画面平均耗时 | 39.91 ms | 7.45 ms |
| 每对画面 P95 | 111.46 ms | 11.51 ms |
| 每对画面最大耗时 | 131.85 ms | 14.31 ms |

修改前请求 `hwaccel auto`，CPU 缩放，未证明实际解码器。修改后两侧均为 NVDEC + GPU 缩放，无回退。不能根据这次短测宣称所有视频持续达到 60 fps，也不是 4K 120 fps 原尺寸直显。

21 项原有对比/显示回归及 3 项新增映射/启动回退检查通过；2 项前端报文检查、前端构建、原生编译及实际显示 shader 执行通过。证据在本机忽略目录 `build/preview-playback-fix`，不随源码分发。

显示 DLL 若被当前后端占用会暂存，新启动脚本在退出旧程序后自动替换。当时未更新安装版，当前改动已纳入 1.0.0 Beta。JPEG Ultra HDR、AVIF 和原生 HDR 显示路径不在这份历史检查范围内。

CUDA 滤镜语义参见 [FFmpeg 官方文档](https://ffmpeg.org/ffmpeg-filters.html#scale_005fcuda)。
