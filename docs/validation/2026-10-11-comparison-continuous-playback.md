# 对比页连续播放修复

## 复现素材

用户提供的 bounce_24fps_5s.mp4（1920×1080、24 fps、H.264、5 秒）与
bounce_24fps_5s_dlss.mkv（3840×2160、96 fps、HEVC、5 秒）。

旧播放每次调用 compare/frame，都为两侧分别启动 ffprobe 定位与 FFmpeg
单帧解码。该素材读取一组完整画面的实测耗时约 3.97–4.26 秒，无法连续播放。

## 实现

- 新增独立 ws/compare 连续显示通道，每侧复用一个 FFmpeg 解码进程。
  不进入增强、插帧或导出管线，不写入原片或导出文件。
- 保留输入 PTS（copyts），两侧按自己的首帧 PTS 归零，用共同播放时间
  选择最近的实际显示帧。非零起始时间与续播定位有真实文件回归。
- 解码队列每侧最多两帧，前端最多保留一组待显示画面；绘制前解码两张
  JPEG，成对更新。过期连接、暂停和跳转前的晚到画面不能覆盖当前状态。
- 连续播放显示宽度最多 1280 像素，最高 60 fps；高帧率流按整数间隔
  选择实际帧，保留其 PTS。此 96 fps 文件连续显示选择 48 fps，不改写文件。
- 暂停/逐帧仍使用原尺寸精确读取，时间轴前后步进仍访问全部实际帧。
- 使用 FFmpeg 的自动硬件解码选择；JPEG 显示经过主机内存，不宣称零回读。
  SDR 使用同一 Rec.709 显示转换；HDR 继续使用固定未校准的 HDR 显示映射。
- 单音轨逻辑保留，按显示时钟校正；这两个用户样本没有音轨，未以其证明
  任意长视频的音画同步性能。

FFmpeg 参数语义参考[官方文档](https://ffmpeg.org/ffmpeg.html)。

## 实测与检查

- 原型连续读取此素材，24 组/秒请求下稳定阶段处理一组 P50 约 26.4 ms，
  包括解码推进、显示转换、JPEG 编码与二进制打包；启动另需约 0.56 秒。
  此数字不等于界面的最终显示帧率。
- 实际 Electron 前端，实际两个文件，两侧 img load 事件统计在共同媒体
  时间 0.4–2.8 秒窗口达到 **40.20 组/秒**，并验证两侧画面完整加载。
  原片自身只有 24 fps，刷新率不表示原片产生了额外源帧。
- 已通过：正常连续播放、暂停后精确步进、跳到 1 秒后半速续播、播放中
  跳到 3 秒继续播放、切换中央滑块与双速、到达 5 秒 EOF、结束后从头重播。
- 15 项 Python 对比/音轨/连续解码回归通过，2 项前端二进制报文检查通过，
  TypeScript/Vite/Electron 构建通过。
- 本轮未重跑 GPU 导出；不据此声称任意 4K/HDR/高帧率素材均达到此性能。

原始证据：bench_out/comparison_playback_20261011/ 下的 decode.json、
electron.json、electron_controls.json、continuous.png（忽略构建证据）。
测试使用独立 18924 后端，不替换用户当前应用；重启运行脚本加载修复。
